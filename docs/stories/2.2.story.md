## Story

**As a** platform administrator,
**I want** to create company records via an API endpoint,
**so that** I can onboard new B2B partners into the FoodTrace platform with pending status.

## Acceptance Criteria

1. POST /api/admin/companies endpoint created and functional
2. Request validates required fields: name, email, domain, type
3. Email uniqueness enforced (returns 409 Conflict if duplicate)
4. New companies created with status: PENDING (no wallet yet)
5. AuditLog entry created for each company creation
6. GET /api/admin/companies endpoint returns list of all companies
7. List endpoint supports optional status filter query parameter
8. Both endpoints are accessible without authentication (auth added in Story 2.5)
9. Code structure prepared for future auth integration (helper function stub)
10. Company email MUST end with `@{domain}` (e.g., if domain is "farm.fi", email must be "something@farm.fi")
11. Proper error responses following rest-api-spec.md format (400, 409, 500)

### Error Response Format

From `docs/architecture/rest-api-spec.md`:

```json
{
  "error": "User-friendly error message",
  "code": "ERROR_CODE",
  "details": { ... }
}
```

**Error Codes to Use:**
- `VALIDATION_ERROR` - Input validation failed (400)
- `AUTH_ERROR` - Authentication required (401)
- `AUTHZ_ERROR` - Insufficient permissions (403)
- `DUPLICATE_ERROR` - Resource already exists (409)

**HTTP Status Codes (Story 2.2 - No Auth):**
- 200 OK - List retrieved successfully
- 201 Created - Company created successfully
- 400 Bad Request - Validation error (including email/domain mismatch)
- 405 Method Not Allowed - Wrong HTTP method
- 409 Conflict - Duplicate email
- 500 Internal Server Error - Server error

**Note:** 401 Unauthorized and 403 Forbidden added in Story 2.5 with authentication.

### AuditLog Note

Since authentication is deferred to Story 2.5, AuditLog entries will have `userId: null` to accurately reflect "system action during development". This will be updated when auth is implemented.

### Authentication Approach (Option B)

**Decision:** No authentication in Story 2.2. Auth will be added systematically to all admin endpoints in Story 2.5.

**Rationale:**
- Avoids chicken-and-egg problem (can't test auth before NextAuth configured)
- Cleaner implementation - auth added once to all endpoints together
- Admin endpoints not publicly exposed during development

**Story 2.5 Scope:** Will add NextAuth.js authentication to:
- POST /api/admin/companies
- GET /api/admin/companies
- POST /api/admin/companies/:id/approve (Story 2.3)
- POST /api/admin/companies/:id/reject (Story 2.3)
- All other admin endpoints created before Story 2.5

**For this story:** Use the auth helper stub in `src/lib/auth/requireAdmin.ts` which returns a mock admin object.

### Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| Endpoints unprotected during dev | Admin endpoints not exposed publicly; auth added in Story 2.5 |
| Forgot to add auth later | Story 2.5 explicitly lists all admin endpoints to protect |
| Prisma unique constraint error | Catch P2002 error, return 409 |
| Invalid CompanyType value | Validate against enum with Zod |
| Email/domain validation too strict | Can be relaxed if business requires different contact email |
| Missing audit log | Use Prisma transaction to ensure atomicity |
