# Story 7.17: Incoming Shipments Visibility

## Status

**Complete** (2025-12-05)

## Story

**As a** distributor or retailer,
**I want** to see incoming shipments on my dashboard without manually searching by product ID,
**so that** I can easily accept products being shipped to me and have a smoother receiving workflow.

## Background

After Story 7.16, distributors can select a recipient when shipping products. Now recipients need visibility of these incoming shipments. Currently they must:
1. Know the product ID through external communication
2. Manually enter the ID in the "Receive New Product" search
3. Add a RECEIVED trace

This story adds the "Incoming Shipments" section to dashboards. Per [SetProduct UI guidelines](https://www.setproduct.com/blog/notifications-ui-design), action-oriented items should be prominently placed above other content.

## Acceptance Criteria

### Incoming Query API
1. GET /api/products accepts `incoming=me` query parameter
2. Query returns products where last trace is SHIPPED AND recipientCompanyId = my company
3. Query excludes products I've already received (no subsequent RECEIVED from me)
4. Requires authentication (401 if not logged in)

### Dashboard Updates
5. Distributor dashboard shows "Incoming Shipments" section above tabs
6. Retailer dashboard shows "Incoming Shipments" section above tabs
7. Section shows count of incoming shipments in header
8. Each incoming shipment shows product info (name, ID, origin, shipped date)

### Accept Workflow
9. Each incoming shipment has "Accept" button
10. "Accept" button opens RECEIVED trace form
11. Location field pre-populated or editable
12. Submitting creates RECEIVED trace (existing TraceRecordForm flow)
13. Product moves from "Incoming" to "In Custody" after acceptance

### Edge Cases
14. Products shipped to wrong company don't appear in incoming
15. Already-received products don't appear in incoming
16. Empty state shows "No incoming shipments" message
17. Loading and error states handled

### Technical Specifications

**Incoming Query Logic:**

```typescript
// GET /api/products?incoming=me
// Returns products where:
// 1. A SHIPPED trace has recipientCompanyId = session.companyId
// 2. No subsequent RECEIVED trace exists from my company

// In src/pages/api/products/index.ts
if (incoming === 'me') {
  const session = await getServerSession(req, res, authOptions);
  if (!session?.user?.companyId) {
    return res.status(401).json({ error: 'Authentication required' });
  }

  // Find products with SHIPPED trace to me, without my RECEIVED
  const products = await prisma.product.findMany({
    where: {
      traceRecords: {
        some: {
          action: 'SHIPPED',
          recipientCompanyId: session.user.companyId,
        },
      },
      NOT: {
        traceRecords: {
          some: {
            action: 'RECEIVED',
            companyId: session.user.companyId,
            // Created after the SHIPPED trace (handled by subquery or post-filter)
          },
        },
      },
    },
    include: { currentOwner: { select: { name: true } } },
    orderBy: { createdAt: 'desc' },
  });

  // Post-filter: ensure SHIPPED is latest action for each product
  // (more complex query, may need refinement)
}
```


### UI Placement Decision

Per [SetProduct](https://www.setproduct.com/blog/notifications-ui-design) and F-pattern scanning research:
- "Incoming Shipments" placed **above tabs** (not as a third tab)
- Action-oriented items should be prominent
- Keeps proven 2-tab structure intact

### Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| Complex query for "incoming" | Start with simpler query, optimize if needed |
| Race condition on accept | Use optimistic locking or make accept idempotent |
| Too many incoming products | Add pagination if needed (defer for POC) |
