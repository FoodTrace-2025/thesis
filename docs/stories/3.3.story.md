# Story 3.3: Implement Supabase Row Level Security (RLS)

## Status

**Deferred** - Production Enhancement

### Deferral Reason (Session 38 - 2025-11-29)

RLS requires a **non-superuser database role** to enforce policies. Current Supabase connection uses the `postgres` superuser which **bypasses all RLS policies**.

**Decision:** Defer to production phase. Prisma tenant client (Story 3.2) provides sufficient application-level isolation for POC/thesis scope.

**What would be required for production:**
1. Create dedicated database role (e.g., `prisma_tenant`) with limited permissions
2. Update `DATABASE_URL` to use non-superuser role
3. Then RLS policies would be enforced

**Reference:** [Prisma + Supabase RLS Discussion](https://github.com/prisma/prisma/discussions/18642)

## Story

**As a** backend developer,
**I want** to implement Row Level Security (RLS) policies on Supabase tables,
**so that** multi-tenant data isolation is enforced at the database level as defense-in-depth.

## Acceptance Criteria

1. RLS enabled on Company, User, Product tables in Supabase
2. RLS policy for Company table: Users can only access their own company record
3. RLS policy for User table: Users can only access users within their company
4. RLS policy for Product table: Users can only access products belonging to their company
5. SQL migration file created in `prisma/migrations/` with all RLS policies
6. Integration test: Direct SQL query with Company A user returns only Company A data
7. Integration test: Direct SQL query with Company A user returns empty for Company B data
8. Documentation: RLS policies documented in `docs/architecture/database-schema.md` (update if needed)

### Technical Specifications

**From Architecture (database-schema.md#row-level-security):**

```sql
-- Enable RLS on Company table
ALTER TABLE "Company" ENABLE ROW LEVEL SECURITY;

-- Policy: Users can only see their own company
CREATE POLICY company_self_isolation ON "Company"
  FOR ALL
  USING (id = current_setting('app.current_company_id')::text);

-- Products: Users can only access their company's products
CREATE POLICY company_product_isolation ON "Product"
  FOR ALL
  USING ("companyId" = current_setting('app.current_company_id')::text);

-- Users: Users can only access users from their company
CREATE POLICY user_company_isolation ON "User"
  FOR ALL
  USING ("companyId" = current_setting('app.current_company_id')::text);
```

**From Epic 3 (Tier 2 RLS approach):**

```sql
-- Enable RLS on Company table
ALTER TABLE "Company" ENABLE ROW LEVEL SECURITY;

-- Policy: Users can only see their own company
CREATE POLICY company_isolation ON "Company"
  FOR ALL
  USING (id = current_setting('app.current_company_id')::text);

-- Policy: Users can only see products from their company
CREATE POLICY product_isolation ON "Product"
  FOR ALL
  USING ("companyId" = current_setting('app.current_company_id')::text);
```

### Session Variable Approach

To use RLS with Prisma, set the session variable before queries:

```typescript
// Utility function to set company context
async function setCompanyContext(prisma: PrismaClient, companyId: string) {
  await prisma.$executeRaw`SELECT set_config('app.current_company_id', ${companyId}, true)`;
}

// Usage in API route
const session = await getServerSession(req, res, authOptions);
await setCompanyContext(prisma, session.user.companyId);
const products = await prisma.product.findMany(); // RLS filters automatically
```

### PLATFORM_ADMIN Bypass Consideration

PLATFORM_ADMIN users need cross-tenant access. Options:
1. **Separate role-based policy**: Add policy allowing PLATFORM_ADMIN role to bypass
2. **Skip RLS for admin**: Use superuser connection for admin operations
3. **Explicit bypass**: Don't set `app.current_company_id` for PLATFORM_ADMIN

Recommendation: Option 1 - role-based policy is cleanest.

### Defense-in-Depth Strategy

| Layer | Mechanism | Story |
|-------|-----------|-------|
| **Application** | Prisma tenant client (`createTenantClient`) | Story 3.2 ✅ |
| **Database** | Supabase RLS policies | Story 3.3 (this story) |
| **API** | Session-based companyId validation | Existing auth |

If Prisma tenant client is bypassed (raw SQL, direct DB access), RLS still protects data.

### Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| RLS breaks existing queries | Test all existing functionality after enabling |
| Session variable not set | Fail-safe: RLS denies if variable missing (secure by default) |
| PLATFORM_ADMIN blocked | Add explicit bypass policy for admin role |
| Consumer product view blocked | Add public read policy for consumer queries |
| Migration rollback complexity | Keep RLS policies in separate migration for easy rollback |

### Consumer Access Consideration

Consumer product queries (via QR code) don't have authentication. Options:
1. **Public read policy**: Allow SELECT on Product for unauthenticated users
2. **Service role bypass**: Use Supabase service role for consumer queries
3. **Skip RLS for consumer route**: Explicitly bypass RLS in consumer API

Recommendation: Option 2 - service role is cleanest for read-only public access.

### Test Strategy

**Integration Tests (Required):**

These tests MUST use real database to verify RLS enforcement:

```typescript
describe('RLS Integration Tests', () => {
  let companyAId: string;
  let companyBId: string;

  beforeAll(async () => {
    // Create test companies and users
    companyAId = await createTestCompany('Company A');
    companyBId = await createTestCompany('Company B');
  });

  it('Company A user can only see Company A products', async () => {
    // Set company context to Company A
    await setCompanyContext(prisma, companyAId);

    // Query all products (RLS should filter)
    const products = await prisma.product.findMany();

    // All products should belong to Company A
    expect(products.every(p => p.companyId === companyAId)).toBe(true);
  });

  it('Company A user cannot see Company B products', async () => {
    // Create product in Company B
    const productB = await createTestProduct(companyBId);

    // Set company context to Company A
    await setCompanyContext(prisma, companyAId);

    // Try to query Company B product by ID
    const product = await prisma.product.findUnique({
      where: { id: productB.id }
    });

    // Should return null (RLS blocks)
    expect(product).toBeNull();
  });

  it('RLS blocks raw SQL access across tenants', async () => {
    // Set company context to Company A
    await setCompanyContext(prisma, companyAId);

    // Raw SQL query (bypasses Prisma tenant client)
    const result = await prisma.$queryRaw`
      SELECT * FROM "Product" WHERE "companyId" = ${companyBId}
    `;

    // Should return empty (RLS blocks at database level)
    expect(result).toHaveLength(0);
  });
});
```

- Tests require Supabase database with RLS enabled
- Use separate test schema or test database to avoid affecting development data
- Consider using transactions with rollback for test isolation
